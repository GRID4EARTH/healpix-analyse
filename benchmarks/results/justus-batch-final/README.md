# Justus版バッチAPIへの移行：最終性能確認

比較元は従来のANALYSE integrationとGEO integrationの組み合わせ。
比較先はGEO PR #252の `42d3bfb6919bbfe33ded96bb56642faeb186e1d5` を土台に、
`/tmp/healpix-geo-batch-followup` のPython接続・互換性対応を加えたローカル修正版と、
`/tmp/healpix-analyse-batched` のANALYSE。PR #252単体を無修正で使った結果ではない。

## 方法

同じ保存済み入力を使い、4条件それぞれ5組、合計40回を独立プロセスで実行。
各組の旧版／修正版の順序は固定乱数種で入れ替えた。
最初に10セルでライブラリを初期化し、フィルターのキャッシュを消去した後に初回を計測。
同じセルIDで値を1だけ増やして再実行し、出力の平行移動も許容誤差1e-12で確認。
計測中にエージェントから他のテスト・ビルドは実行していない。
macOS arm64、同一マシン・Python 3.13環境、sigma=20 m、既定キャッシュ容量で比較。
GaussianのWGS84距離計算は引き続きpyproj.Geod。

## 中央値

正の変化率は修正版の所要時間増加、負は短縮。

| level / size(m) / truncate | 初回：旧(s) | 初回：新(s) | 変化 | 再実行：旧(s) | 再実行：新(s) | 変化 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 19 / 600 / 4 | 0.043135 | 0.043506 | +0.86% | 0.003121 | 0.002997 | -3.99% |
| 20 / 600 / 5 | 0.776757 | 0.771537 | -0.67% | 0.061775 | 0.060960 | -1.32% |
| 19 / 3600 / 4 | 1.561686 | 1.566667 | +0.32% | 1.569193 | 1.563751 | -0.35% |
| 20 / 1200 / 5 | 3.433233 | 3.444451 | +0.33% | 3.430040 | 3.423830 | -0.18% |

初回の中央値は−0.67%〜＋0.86%。今回の条件では実用上の大きな性能低下は見られない。
ただし、あらゆる環境・入力で遅延ゼロを保証する結果ではない。
19/3600と20/1200のケースはキャッシュに収まらず、再実行でも計算が走る。
全20組の初回出力はNaN位置も含めて完全一致し、最大絶対誤差は0。
各回の値とペアごとの差は summary.json、全実行は timings.json に保存。

## 最終コード確認

計測後のClippyチェックで、型から必ず成立するif-let分岐を指摘されたため、
同じ2要素の直接分解に整理した。アルゴリズム・スレッド数・返り値は変更していない。
上の性能計測はこの等価な構文整理の前。整理後はリリースビルドを再作成し、
GEO円領域検索66件＋ANALYSE408件、合計474件成功、21件skipを確認。
Rust Clippyはworkspace/all-targets/-D warningsで成功。git diff --checkも成功。

検証後、GEO PR #292へ同じファイル内容を取り込み、ANALYSEのPixi依存先を
`508ef39850a7bb0e8e07b0360ca7a9a5326d69d5` に更新した。
元のPR #252を祖先に持ち、追加修正コミットは `2209051`。

公開前の追加確認で、GEOのnum_threads=0にも最大8スレッド制限を適用する補正を追加した。
ANALYSEの計測経路は8を明示しており、この補正で変わらない。
最終公開GEOコミットは `5a43c343d2f5940ae87a730fbedb856e0256ef4a`。
最終リリースビルドでGEO69件＋ANALYSE408件、計477件成功、21件skip。
